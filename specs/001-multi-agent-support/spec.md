# Spec 001: Multi-agent customer service for Getnet merchants

Status: ready for implementation · Owner: André Melo · Source: `AI_Hardcore_Engineer_Multi-Agent.md`

## Problem

Getnet merchants ask two very different kinds of questions in the same channel: how a
product works ("How does receivables advance work?") and what is happening with their own
account ("When will yesterday's sales be deposited?"). A single assistant either invents
product facts or has no access to account data. We need an orchestration of specialised
agents behind one HTTP endpoint, with a human handoff for what it cannot resolve.

## Users and scenarios

A merchant, identified by `user_id`, sends one message and gets one answer. S1 to S10 are
the challenge's *Example Test Scenarios*, verbatim; G1 to G5 and H1 to H2 cover guardrails
and escalation. All use `cliente1988` unless stated.

## Functional requirements

- **FR-001** `POST /v1/chat` accepts `{"message": str, "user_id": str}` and returns, inside
  the envelope `{data, meta}`, the answer, the route, the agents, the tools used, the
  verified sources, the escalation ticket, the language, the request id and the latency.
  `GET /health` reports the service status and the number of chunks in the knowledge base.
- **FR-002** A **Router agent** classifies every message into `knowledge`, `support`, `human`
  or `unsupported` and detects its language. Off-topic requests, prompt injection and
  requests for another merchant's data are `unsupported`.
- **FR-003** A **Knowledge agent** answers product questions with RAG over Getnet's official
  website and general questions with a web search tool.
- **FR-004** A **Customer Support agent** answers account questions with tools that read the
  merchant's data (profile, sales and settlements, transactions, terminals), plus the
  knowledge base for troubleshooting.
- **FR-005** A **Human Escalation agent** writes the handoff (category, priority, operator
  summary, customer message) when the merchant asks for a person, when a specialist cannot
  resolve the case or when a specialist fails. The ticket id is generated by code.
- **FR-006** Answers are in the merchant's language, although the sources are Portuguese.
- **FR-007** Cited sources must be URLs actually returned by a tool.
- **FR-008** The knowledge base is ingested from the curated list `data/sources.json`. The
  ingestion is idempotent, logs each page and the totals, and runs at container start when
  the store is empty.
- **FR-009** The service builds and runs with `docker compose up --build`; the container is
  named `getnet-challenge`.

## Non-functional requirements

- **NFR-001 Security:** support tools act only on the request's `user_id`; the model cannot
  choose whose data to read.
- **NFR-002 Privacy:** card numbers, CPF, CVV and passwords are masked before the LLM and in
  the traces.
- **NFR-003 Reliability:** a failing tool or agent degrades to a partial answer or a human
  handoff, never to an unhandled error. The handoff works with the LLM down.
- **NFR-004 Observability:** every request is one LangSmith trace and one structured log
  line, correlated by `request_id`.
- **NFR-005 Quality:** a scenario dataset scores routing, tool use, escalation and data
  leakage; it runs locally and as a LangSmith experiment.
- **NFR-006 Latency:** a typical answer takes under 8 s.
- **NFR-007 Testability:** the automated suite runs offline, without API keys; a live debug
  CLI shows each node of the graph; manual test cases document the live
  checks.

## Acceptance criteria

- **AC-1** Evals on `evals/dataset.jsonl` (S1 to S10, G1 to G5): `route_correct`,
  `tools_expected`, `escalation_expected` and `no_card_leak` at 100%.
- **AC-2** `uv run pytest` green without keys; `ruff` and `pyright` (strict) clean.
- **AC-3** Ingestion loads 42 of 42 pages; a second run leaves the chunk count unchanged.
- **AC-4** `docker compose up --build`: container `getnet-challenge` healthy, `/health`
  reports more than zero chunks.
- **AC-5** H1 and H2 open a ticket through `scripts/chat.py`.
- **AC-6** The README covers everything the challenge lists under *README.md must cover*.

## Out of scope

Conversation memory across requests, real authentication, a real customer database and
ticketing system, streaming responses over HTTP.

## Assumptions

- `user_id` arrives in the body, as the challenge defines; in production it would come from
  the auth token.
- Customer data is a fictitious mock (`data/customers.json`), with dates relative to today.
- The suggested `www.getnet.net` is Getnet's global and Portugal site. Brazilian product
  content lives on `site.getnet.com.br`, which is the main source.
- The source list is curated, not crawled: the help center lists its articles through
  JavaScript, so no crawler reaches them (measured; see `INITIAL-PROMPT.md` §3).
